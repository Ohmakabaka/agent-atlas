# 内容、主题与关系贡献

## 文件与数据形态

`data/` 保存独立 JSON 数据：

- `topics.json`：主题树、问题、概念和阅读路径。
- `articles.json`：资料、中文导读、技术要点和可选工程案例。
- `sources.json` / `organizations.json` / `people.json`：来源、机构和人物。
- `relations.json`：带证据、类型与审核状态的知识关系。
- `editorial/*.json`：Codex 会话辅助撰写的原创指南、主题与引用；对应可读原稿由命令生成到 `content/guides/`。

种子程序按固定 ID 或规范地址追加缺失数据，不覆盖数据库现有编辑。修改 JSON 是修改未来初始化模板；修订已有线上内容需通过后台完成，或单独编写审阅过的数据迁移。

## 技术主题格式

以下展示字段形状；新增主题须采用唯一 ID、slug 并选择真实父主题：

```json
{
  "id": "topic-example",
  "slug": "example",
  "name": "中文主题名",
  "englishName": "English term",
  "description": "技术范围、适用边界与资料线索。",
  "question": "这个主题帮助读者解决什么具体问题？",
  "concepts": ["关键概念"],
  "readingPath": ["已存在的文章-slug"],
  "featured": false,
  "sortOrder": 0,
  "color": "teal",
  "parentId": "已存在的父主题-id"
}
```

顶层主题的 `parentId` 为 `null`。阅读路径只引用已发布资料的 slug，允许跨主题编排，并保留编辑指定顺序。后台会检查引用；资料后来归档时，不再出现在公开阅读路径中。不要形成父子循环。专题介绍应有可跟进的原始资料，不添加缺乏证据的技术结论。

## 资料收录

资料必须能明确回答：它是什么、谁发布、何时发布、为什么与这个主题有关、原始证据在哪里。

- 中文标题应准确表达原文范围；保留原始标题，不虚构“官方”“最佳”等标签。
- 中文导读用独立表达概括范围、核心方法和局限，不把摘要扩大为未经证实的工程结果。
- 作者和所属机构按原文标注。GitHub 项目所属团队不一定等同于某篇文章全部作者的雇主。
- 缺少发布日期时留空；仓库创建时间、收录时间与特定版本发布时间不可混用。
- 工程案例分别填写问题、架构、方案、效果和依据链接。没有性能数字就不填数字，没有生产证据就不称为生产部署。
- `type` 为 `paper/article/docs/repository/podcast`。
- `layer` 为 `primary/community/engineering`，分别表示原始资料、中文解读和工程实践。
- `quality` 为 `curated/standard`，是编辑整理等级，不是来源真实性的自动保证。
- 常规采集草稿和运行时模型建议先进入待审流程，核对后发布；“已发布”与“经过人工复核”是不同状态。首批 Codex 原创指南采用下节的明确标注规则，不能视为人工审核结果。

首批资料来自真实公开链接。开发环境对部分网站的访问限制意味着仍需社区持续核验元信息；纠错时请附可验证的原始依据，不仅提供模型回答或转述。

## Codex 原创指南与模型草稿

本次网站内容请求形成了六篇原创指南，分别覆盖架构选型、上下文预算、MCP 权限、长期记忆、评测回归和可靠执行。内容及续写命令见 [Codex 内容工作流](codex-content.md)。这些指南使用当前 Codex 会话额度编写，不需要网站模型 API 密钥；部署后的服务不能直接把 Codex 用量当作 API 余额。

首批六个 slug 是代码中显式选定的启动内容：seed 追加缺失条目并发布，统一署名“Agent Atlas · Codex 辅助整理”，保留来源核查记录，`reviewedAt` 为 `null`。页面说明尚未人工复核，不将自动核对来源伪装成人审。这个启动内容安排不会扩大为以后新增内容的自动发布规则。

续写内容保存到 `data/editorial/*.json` 后，先运行 `npm run content:render`，再运行 `npm run content:check`。JSON 与生成的 Markdown 必须一致，且一起提交。`npm run content:import` 默认追加为待审核；显式使用 `--publish` 只发布本次新建条目，也不会填写人工复核时间。重复导入跳过已存在内容，既有编辑、待审状态和归档状态均不会被覆盖。线上修订使用后台；修改 JSON 不会自动改写已导入的正文。

网站运行时的“生成中文导读建议”使用单独配置的模型 API，只根据条目元数据生成建议，保存到私有 `aiDraft`。它不会自动替换公开内容、发布文章或确认知识关系；编辑核对后再手动采纳。采集原始元数据、模型草稿与公开编辑内容保持分离。没有模型 API 密钥时，这条可选路径不可用，手工编辑和 Codex 内容包流程仍可使用。

## 后台修订与历史

后台可以维护资料、主题、阅读路径、来源和知识关系。文章保存会建立版本快照，并验证当前版本，防止旧窗口覆盖别人的修改。遇到冲突时先核对最新内容，保留有价值的输入后重新编辑，不以删除数据绕过版本校验。

历史恢复只恢复可编辑字段与关联，创建新版本并回到待审核，不直接重新发布旧内容。驳回和归档保留理由与历史。审计记录辅助追踪操作，不代替原始资料证据。

主题可以有多层父子，但不能循环；已有资料、子主题或关系引用的主题不能直接删除或修改 URL 标识。可修改显示名称，或先明确处理引用。

## 知识关系

| 类型               | 含义与证据要求                                                   |
| ------------------ | ---------------------------------------------------------------- |
| `explains`         | 内容解释某项技术，原文中有对应论述                               |
| `implements`       | 项目或案例实现某项技术，有代码或设计说明                         |
| `discusses`        | 对某技术提出讨论，避免误称完整实现                               |
| `compares_with`    | 明确比较两个方案，保留比较的范围                                 |
| `references`       | 原文明确引用目标内容                                             |
| `extends`          | 作者明确说明扩展已有工作，附出处                                 |
| `challenges`       | 明确质疑某结论或方法，保留语境                                   |
| `related_to`       | 一般主题关联，不暗示引用或继承                                   |
| `prerequisite_for` | 起点是终点的前置知识，需要教学或技术依据，不仅凭编辑阅读顺序推断 |
| `evolves_from`     | 起点演进自终点，需要明确历史/技术依据，不能仅凭发布时间推断      |

新建议使用 `suggested`；确认后使用 `confirmed` 并提供 `evidenceUrl`。关系需要恰当的方向和恰好两个端点，不允许自关联。后台可复核和修订；前台只展示已确认且文章端点已公开的关系。

## 版权与署名

收录不是全文授权。第三方论文、博客、公众号、商标和开源项目各自保留版权与许可；本项目 MIT 许可证不覆盖这些外部材料。

默认贡献原创中文导读、元信息、原文链接与关系。不提交未授权全文、绕过付费墙获得的内容或私人群聊。确需引用时使用必要且有限的摘录，明确作者、出处和许可；无法确认授权时仅提供链接与自己的导读。

若作者要求修正署名、移除不当摘录或说明权利，请通过 issue 提供具体条目和依据。不要在公开 issue 暴露私人联系方式、访问令牌或其他敏感材料。
