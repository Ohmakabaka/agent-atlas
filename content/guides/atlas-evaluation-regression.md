# Agent 评测落地：从任务定义到持续回归

以 SWE-bench、WebArena 和模型裁判工具为线索，建立任务定义、可执行判定、成本记录与失败回归的完整流程。重点是让每次改动可比较，而非追逐一个脱离业务约束的总分。

作者：Agent Atlas · Codex 辅助整理

来源核查日期：2026-11-14

本篇为 Codex 会话辅助撰写的原创技术指南；已核对列出的来源，未标注为人工审核。工程建议与来源陈述应分开理解。

## 先写清楚什么叫完成

“回答看起来合理”很难判断 Agent 是否解决了任务。假设你在做客服 Agent，目标是为符合规则的订单建立退款申请。成功条件应包括订单匹配、资格核对、正确申请记录和清晰回复；回复中说“已处理”不能替代业务数据库中的结果。这个例子是编辑设计的教学场景，不是已验证的产品案例。

SWE-bench 把代码仓库和 GitHub 问题交给系统，要求生成修复补丁，并提供可复现的评测环境。WebArena 则提供网站交互任务，要求正确配置网站并在实验后恢复初始环境。二者给出的共同线索是：任务输入、执行环境和结果判定需要一起定义。一个基准通过率只说明对应任务集合与运行条件下的表现。

## 把业务需求变成任务卡

建议每个案例至少保存六项：初始数据、用户目标、允许动作、禁止动作、完成判定和资源预算。例如退款案例允许读取订单和创建申请，但不能修改订单原价；正确结果是指定订单出现一条金额一致的申请，且其他订单没有变化。再增加资格不符、重复请求和工具超时等变体。

任务卡中的数据版本、工具版本、提示词版本和模型标识必须可追溯。若环境依赖时钟或外部搜索，固定测试时间或记录当时返回的证据。不要把同一任务第二次运行留下的业务状态当作干净起点，否则改动前后的结果已经失去可比性。

## 分开看结果、过程与代价

结果层优先使用可执行规则，例如数据库断言、测试命令和输出结构校验。过程层检查是否越过权限边界、是否遗漏必要步骤、是否重复执行带副作用的动作。代价层记录总耗时、模型调用量、工具调用量、重试次数和人工接管次数。最终成功但进行了多次重复退款，仍应判为失败。

开放式说明文字可以增加模型裁判。FastChat 的 LLM Judge 文档提供单回答评分、成对比较和人与模型判定一致性分析的方法；这支持把裁判作为一种评测工具，并不保证它适合你的业务。编辑建议先用少量人工标注案例校准评分标准，保存裁判模型、提示词和原始理由，对关键失败保留复核入口。能由程序确认的事实，不应只交给另一个模型判断。

## 用配对实验解释改动

先在同一组任务和同一预算下运行旧版本与新版本，再查看每个任务的变化。总成功率提高时，也要找出“原来成功、现在失败”的案例，并按工具选择、信息缺失、状态污染、执行错误或判定错误分类。对于存在随机性的任务，可以重复运行并报告波动；单次漂亮结果不足以证明稳定改进。

SWE-bench 当前文档特别说明，结果缓存依赖运行标识与实例标识，更换补丁却复用标识可能直接读取旧结果。这个具体实现提醒我们：实验缓存也是实验条件的一部分。自己的评测系统应为每次对比记录配置摘要，并核对是否真的执行了新版本。

## 让线上问题进入回归集

遇到真实失败后，先移除个人信息和凭证，再提炼一个可独立重现的任务。保留必要边界条件，避免只是复制一整段聊天。新用例加入固定回归集后，提示词、模型、工具 schema 和检索策略的变更都应触发相应测试。

以下是编辑建议的首次落地清单：

- 选择覆盖常见需求与失败边界的一组任务，写出机器可判定的成功条件。
- 固定初始状态和版本，保留一次完整执行记录，并验证失败时也能留证。
- 把成功率、成本、越权和人工接管分别展示，避免压成无法解释的总分。
- 对一次实际失败建立回归用例，确认旧版本失败、修复版本通过。
